# lean-proof：AI + Lean 4 自动证明流水线

## 角色与铁律

- **编译器是唯一裁判**。任何未经 `lake env lean` 实际验证的"证明完成"宣告一律视为失败。
- **你负责草拟，Lean 负责裁决**。你的任务是让编译通过，而不是让文本读起来可信。

## 输入

1. 命题的自然语言描述，包含全部假设（可积性、独立性、有限性、参数范围等）。
2. Lean 项目根目录（含 lakefile）。若依赖 mathlib，须已完成预编译缓存获取（参见配套教程第 16 章）。

## 流程（四阶段）

### 阶段 A：陈述形式化

1. 把命题翻译为 `theorem` 陈述，证明体只写 `:= by sorry`。
2. 运行 `lake env lean <文件>`。只有"除 sorry 警告外零输出"才算陈述合格。
3. 列出每个数学假设到 mathlib 概念的映射（如"可积 → `Integrable`""均值 → `∫ x, f x ∂μ`"），与用户确认后进入下一阶段。陈述译错，后面全白费，这一步值得花时间。

### 阶段 B：骨架分解

1. 依据证明思路生成引理链：主定理与各引理全部用 `sorry` 占位。
2. 整体编译，达到"零 error、仅 sorry warning"。
3. 确认引理链无循环依赖、无未使用引理。

### 阶段 C：逐引理填坑（核心循环）

对每一个 sorry，执行：

1. 草拟 tactic 序列，按优先级：自动化（`simp` / `omega` / `linarith` / `ring`）→ 重写（`rw [引理]`）→ 结构（`induction` / `rcases`）→ 手工构造（`exact` / `refine`）。
2. 写入文件，`lake env lean <文件>` 检查。
3. 若有 error：把**完整输出**（错误信息 + 剩余目标 `⊢` 行）作为上下文修正后重试；同一目标最多 8 轮。
4. 升级路径（依次尝试）：换 tactic → 插入 `have` 中间引理 → 把目标拆成更小的引理 → 回阶段 A 质疑陈述本身。

### 阶段 D：终检

- `grep` 源文件确认无 `sorry` 残留；
- 对主定理执行 `#print axioms <定理名>`，确认无意外公理依赖；
- 输出报告（见下）。

## 反馈接口规范

- 命令：在项目根目录执行 `lake env lean <文件路径>`。单文件秒级返回，比全量 `lake build` 适合高频循环。
- 输出解析约定：`error:` 开头的行是失败原因；`⊢` 行是剩余目标状态；`warning:` 中 `declaration uses 'sorry'` 的条数即剩余进度。
- 陷阱：`lake build` 可能因增量缓存显示虚假成功，一切以 `lake env lean` 输出为准（实测教训，见教程附录 B）。

## 输出格式

1. 最终 Lean 源码（完整、可直接编译）；
2. 形式化说明：每个数学假设如何映射到 Lean 概念；
3. 迭代日志摘要：总轮数、主要卡点与解法；
4. 未决问题（若终检未通过，如实列出剩余 sorry 与原因）。

## 限制与诚实条款

- 若陈述本身是假命题（例：`3 ^ n % 3 = 0` 对 n=0 不成立），编译器会拒绝一切证明。此时应报告"疑似假命题或陈述需修正"并给出反例分析，而不是死循环重试。
- 不得虚构 tactic 名或引理名。引用任何库引理前，先 `#check @名字` 验证其存在与精确陈述。
- 网络或环境问题（如代理 502）导致无法验证时，明确告知"未验证"，不得声称完成。
